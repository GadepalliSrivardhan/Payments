5.1 Overview of SWIFT

SWIFT (Society for Worldwide Interbank Financial Telecommunication) is a member-owned cooperative founded in 1973, headquartered in La Hulpe, Belgium. It operates the world's leading secure financial messaging network used by over 11,000 financial institutions in 200+ countries. SWIFT does NOT move money — it carries messages (instructions) between financial institutions. The actual movement of funds happens through correspondent banking relationships and settlement systems.

Important: SWIFT is a messaging network only. When Bank A sends a SWIFT MT103 to Bank B, it is instructing Bank B to pay. The actual debit/credit happens through the nostro/vostro relationship between the two banks.

5.3 ISO 20022 — The New Global Standard

Introduction to ISO 20022

ISO 20022 is an international standard for financial messaging developed by ISO (International Organisation for Standardisation). Unlike SWIFT MT messages which are text-based with fixed fields, ISO 20022 uses XML (eXtensible Markup Language) — a structured, data-rich format that can carry far more information in a standardised, machine-readable way. ISO 20022 messages carry structured data (names, addresses, LEIs, purpose codes) rather than free-text, enabling much better straight-through processing, fraud detection, and regulatory compliance.

ISO 20022 Identifier Format — The Syntax Structure

Every ISO 20022 message has a unique identifier following this format: xxxx.nnn.aaa.bb

Format: xxxx . nnn . aaa . bb Example: pacs . 008 . 001 . 08
ComponentLength & TypeMeaningDescription
xxxx4 alphabetic (4!a)Business ProcessCategorizes the process the message relates to (e.g., pacs = Payment Clearing And Settlement)
nnn3 alphanumeric (3!c)Message FunctionalityDefines the functionality (e.g., 008 = FItoFICustomerCreditTransfer)
aaa3 numeric (3!n)VariantIdentifies specific market practices (e.g., 001 = variant 001)
bb2 numeric (2!n)VersionVersion number incremented with each update (e.g., 08 = version 8)
Example: pacs.008.001.08 — pacs = Payment Clearing & Settlement | 008 = FI to FI Customer Credit Transfer | 001 = Variant 001 | 08 = Version 8

5.4 ISO 20022 Mandatory vs Optional Fields

In XML/ISO 20022 messages, the cardinality (how many times an element must appear) is defined by Min and Max values in the XSD (XML Schema Definition):

MinMaxMeaningExample
01Optional — may appear onceIntermediary Agent (optional in pacs.008)
0*Optional — unlimited repetitionsCharges Information (zero or more)
11Mandatory — must appear exactly onceGroup Header in pacs.008
1*Mandatory — one or more repetitionsCredit Transfer Transaction Information
Important: Cardinality alone doesn't tell the full story. You must consider: (1) the full XML hierarchy — if a parent element is optional (Min=0), all its children are also effectively optional even if they show Min=1; (2) Choice elements (XOR) — only one of the children under a choice element can be selected; (3) CBPR+ business rules — additional rules beyond XSD, e.g., "If AnyBIC is absent then Name is mandatory."

Hierarchical Structure Example (pacs.008)

// Path: /Document/FIToFICstmrCdtTrf/GrpHdr/SttlmInf/SttlmAcct/Id/Othr/Id // Even though SttlmAcct/Id/Othr/Id has Min=1, Max=1 (mandatory at its own level), // the PARENT SttlmAcct has Min=0 (optional). So SttlmAcct/Id/Othr/Id // is effectively OPTIONAL in the full message context. Group Header Min=1, Max=1 ← Mandatory Settlement Info Min=1, Max=1 ← Mandatory Settlement Method Min=1, Max=1 ← Mandatory Settlement Acct Min=0, Max=1 ← Optional ← KEY Id Min=1, Max=1 ← Mandatory IF parent present Othr Min=1, Max=1 ← Mandatory IF parent present Id Min=1, Max=1 ← Mandatory IF parent present

Choice Elements

A choice element (indicated by a specific symbol in MyStandards) means exactly one of its children must be selected — they are mutually exclusive. For example, in pacs.004 Return Chain, the Creditor element is a choice between Party or Agent. You must choose one. If Party is selected, the Agent sub-elements (including FinancialInstitutionIdentification) will not be present even though they are marked Min=1 at their own level.

5.5 MT vs MX — Agent and Parties Comparison

One of the most important conceptual shifts in the ISO 20022 migration is the terminology change: in MT messages, the terminology is Institution/Bank (for financial institutions) and Customer (for individuals/companies). In MX messages, financial institutions are called Agents and individuals/companies are called Parties.

Transaction Views — From Different Perspectives

The same payment chain looks different depending on which institution is the "sender" of the pacs.008/MT103. From the Debtor Bank's view (view 01): the Debtor Bank is the Instructing Agent (header sender). From a Correspondent's view (view 02): the correspondent is both Instructed Agent (receiver) and Instructing Agent (new sender) — it adds a Settlement Method tag (dedicated in MX, no equivalent in MT). From an Intermediary's view (view 03): the Previous Instructing Agent tag is populated in MX (dedicated tag) — in MT, the /INS/ keyword in field 72 is used instead.

5.6 CBPR+ Hybrid Address Implementation

ISO 20022 CBPR+ (Cross-Border Payments and Reporting Plus) is the SWIFT standard for ISO 20022 cross-border payments. One key topic is how postal addresses are handled in MX messages.

<PstlAdr> <PstlCd>112233</PstlCd> <Ctry>SG</Ctry> ← Mandatory in Hybrid <TwnNm>Singapore</TwnNm> ← Mandatory in Hybrid <AdrLine>Block 999, LK Street</AdrLine> ← Unstructured line 1 <AdrLine>Floor 3</AdrLine> ← Unstructured line 2 </PstlAdr>

5.8 SWIFT GPI & Overview of SWIFT Payment Processing Components

SWIFT GPI (Global Payments Innovation) launched in 2017 transformed cross-border payments by introducing: end-to-end tracking via a unique transaction reference (UETR — Unique End-to-end Transaction Reference), same-day use of funds in the beneficiary's time zone, transparency of fees deducted by each bank in the chain, and unambiguous credit confirmation to the beneficiary account.

📍

GPI Tracker

A central cloud-based system where all banks update payment status. Corporates and banks can track payments in real time using the UETR.

✅

Universal Confirmation

Mandatory for all GPI banks — must confirm credit to beneficiary account with timestamp, amount credited, and exchange rate applied.

🛡️

Payment Controls

Real-time sanctions and fraud screening applied at SWIFT infrastructure level before message delivery — adds an extra layer of security.

⚙️

Transaction Manager

Orchestrates the full payment lifecycle. Manages exceptions, retries, and end-to-end payment status. Key for ISO 20022 migration management.

Migration Impacts

The migration from SWIFT MT to ISO 20022 MX is the largest transformation in financial messaging in 50 years. Key impacts include: (1) Data richness — MX messages carry structured name/address data instead of free text; (2) System changes — banks must upgrade payment engines, transformation layers, and AML systems; (3) Coexistence — SWIFT ran a coexistence period (2023–2025) where both MT and MX were accepted; (4) Mandatory cutover — from November 2025, MT messages for cross-border payments are no longer accepted on SWIFT for most message types; (5) Data truncation risk — if a bank translates MX to MT (for legacy systems), the richer MX data gets truncated, losing beneficiary address details.

Euro Liquidity Bridge — A Real-World Migration Example

The Bank of England's Euro Liquidity Bridge illustrates the real-world complexity of ISO 20022 migration. CHAPS Direct Participants use euro cash sent via TARGET2 as collateral to raise intraday sterling liquidity in RTGS. When TARGET2 migrated to ISO 20022 on 20 March 2023, the Bank of England's legacy RTGS could not process the new ISO 20022 format messages from DNB (De Nederlandsche Bank). The Bank ran the bridge manually (as a last-resort service, once per day, on request) until its new RTGS core ledger launched (Summer 2024 — Transition State 3). After TS3, the bridge returned to straight-through processing but accepts only MX format messages.

Key Requirement: In the interim period, DPs must contact PSC before funding the Bank's euro collateral account at DNB. Both MT and MX were accepted for funding during transition. After TS3, only MX is accepted. BIC for Bank's euro cash collateral account: FLORNL2ACAC.
